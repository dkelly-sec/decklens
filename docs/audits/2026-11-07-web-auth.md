## Confirmed defects

### F1 (Medium): no Host allowlist, so DNS rebinding reaches the "local only" no-login mode
- Location: `src/decklens/web/security.py:100`. Class: Cross-site request forgery / missing Host validation (CWE-350).
- Evidence chain:
  1. `src/decklens/web/security.py:100` accepts a POST when the Origin's netloc equals the request's own
     Host header. Both values are chosen by the page that sends the request.
  2. A page on the attacker's hostname (port 8000) whose name is re-pointed to 127.0.0.1 sends
     that hostname as Host and a matching Origin; the 127.0.0.1 bind does not help, because
     the owner's own browser makes the connection.
  3. Nothing checks Host against an allowlist: the middleware stack at `src/decklens/web/app.py:119` has
     only the Origin check. `DECKLENS_LOGIN=off` is refused only over HTTPS (`src/decklens/web/app.py:561`),
     so with logins off `require_user` lets every route through.
- Scenario: the owner runs DeckLens with `DECKLENS_LOGIN=off`, which README.md presents as safe on your own
  computer, and opens a hostile page. The page calls the player, record and search routes on the owner's
  IP-whitelisted API key, posts fake watcher reports and, inside the desktop app, calls `/api/desktop/quit`.
  With logins on (the default) the same page only reaches `/api/login`.
- Fix approach: add Starlette's `TrustedHostMiddleware` next to `SameOriginMiddleware` with
  `127.0.0.1`, `localhost`, `[::1]` and the configured HTTPS hostname, rejecting other hosts in the same pure
  ASGI style as the existing guards. Existing tests use `testserver`, which the test setup will need to allow.
- Reproduction (`tests/test_audit_web_auth.py`):
  - `test_rebound_hostname_cannot_use_the_no_login_api`: expected to fail on the current code (it gets 200);
    ran, fails as expected.
  - `test_local_hostnames_still_work_without_logins` (127.0.0.1 and localhost): expected to pass; ran, passes.

### F2 (Medium): re-adding a removed username brings its old session cookies back
- Location: `src/decklens/users.py:44`. Class: Authentication and sessions (CWE-613).
- Evidence chain:
  1. `src/decklens/users.py:44` inserts a new account without a `session_version`, so it starts at the column
     default of 1 (`db/migrations/004_web_users.sql:12`).
  2. The cookie signs only username, version and issue time (`src/decklens/web/auth.py:122`), and
     `src/decklens/web/auth.py:236` accepts it when the stored version matches.
  3. Revocation works by bumping the version; deleting the row and inserting a new one resets it, so a cookie
     issued at version 1 within the last 30 days matches again.
- Scenario: a friend's session cookie leaks and the owner runs `users remove friend`, later `users add friend`
  for the same friend or someone new. Whoever holds the old cookie is signed in to the new account without
  its password.
- Fix approach: start each new account at a version that no earlier account of that name used, for example
  `secrets.randbelow(2**31)` in `add_user`, keeping the existing version comparison in `Auth.session_user`.
- Reproduction (`tests/test_audit_web_auth.py`, needs `DECKLENS_TEST_DATABASE_URL`):
  - `test_removed_users_cookie_stays_dead_after_the_name_is_added_again`: expected to fail; ran against
    Postgres 16, fails as expected (the old cookie returns the new user at version 1).
  - `test_a_freshly_added_user_can_log_in_and_keep_a_session`: expected to pass; ran, passes.

### F3 (Medium, planned HTTPS deployment): login runs any number of 128 MB scrypt checks at once
- Location: `src/decklens/web/auth.py:223`. Class: Rate limiting and quota (CWE-770).
- Evidence chain:
  1. `src/decklens/web/auth.py:223` runs scrypt at N=2^17, r=8 (about 128 MB) for every attempt, including
     unknown usernames, by design.
  2. `POST /api/login` (`src/decklens/web/app.py:456`) needs no login and runs in the 40-thread pool.
  3. The only control, `limit("login")`, caps 10 attempts a minute per client but not how many run at the
     same time; the reviewer measured 8 parallel checks taking the process from 12 MB to over 1 GB.
- Scenario: after deployment, one unauthenticated client sends its 10 allowed attempts at once (about
  1.3 GB); a few addresses fill all 40 threads, enough to have the process killed on a small server.
- Fix approach: guard `verify_password` in `Auth.login` with a `threading.BoundedSemaphore(2)` and answer
  the existing 429 when it is busy, in the same locking style as `LoginGuard`.
- Reproduction (`tests/test_audit_web_auth.py`):
  - `test_password_checks_do_not_all_run_at_once`: expected to fail; ran, fails as expected (peak 10).
  - `test_one_login_at_a_time_still_works`: expected to pass; ran, passes.

## Refused or unconfirmed candidates
- R1, 500 responses without security headers: refused as a finding, lens exploitability; kept as Low. The
  `Exception` handler at `src/decklens/web/app.py:172` is served outside `SecurityHeadersMiddleware`; the
  body is fixed JSON, so no script can run in it.
- R2, non-ASCII cookie gives a 500: refused as a finding, lens exploitability; kept as Low.
  `hmac.compare_digest` raises on non-ASCII strings at `src/decklens/web/auth.py:132`; another site cannot
  plant that cookie, so it only breaks the sender's own requests.
- R3, logout only clears the browser cookie: refused, lens claim correctness (by design). The web role cannot
  write `web_users`, so logout cannot bump the version; `users logout-all` revokes server-side. Kept as Low:
  the page's Log out does not say a copied cookie stays valid.
- R4, Origin check ignores the scheme: refused, lens exploitability; kept as Low. Needs a network attacker
  before HSTS plus a browser without schemeful SameSite.
- R5, flood `clear()` wipes lockouts: refused, lens exploitability. Every attempt pays a scrypt check and
  10 per minute per client, so the reset costs far more than the 15-minute wait it saves.
- R6, lockout bypass by case or Unicode: refused, lens claim correctness. The lockout key and the username
  are stripped and lowered the same way; variants that differ normalise to nothing and cannot log in.
- R7, web role over-privileged: refused, lens existing mitigation. `db/web_role.sql:18` grants SELECT only,
  no default privileges exist, and the integration test that the role cannot write ran and passed.
